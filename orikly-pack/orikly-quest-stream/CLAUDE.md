## Требования к трансляции

- **0.4.12 (решение Paul):** сетка **360/60**; View по умолчанию **Left half** (только левый глаз/левая половина, `defaultView` в `view.go`), чтобы убрать фризы. Разворот по-прежнему 960/80.
- **Качество постоянное (решение Paul, 0.4.10):** сетка 480/60, разворот 960/80, без снижения (лестницы по одной ступени; прежние — в комментарии `StreamState.kt`). Предупреждено: на плохом канале это даёт больше фризов.
- **Захват 16:9 (0.4.11):** `VirtualDisplay` всегда 1706×960 (`CAPTURE_WIDTH`/`HQ_HEIGHT`): система сообщала размер экрана 500×800 (окно панели), картинка выходила узкой. Как выглядит содержимое в 16:9 на настоящих очках — не проверено.
- **View (0.4.11):** на странице «Full / Center 75% / Center 50% / Left half / Right half» — какую часть кадра по ширине слать (`view.go`, `"crop": [l, r]` в `want`, `cfg.View`). Очки вырезают полосу и масштабируют до 480 (или 960) по высоте → кадр уже и легче (Center 50% ≈ вдвое меньше трафика). Центр кадра в VR = куда смотрит ученик. «Left/Right half» — на случай двух глаз в кадре. Плитки на странице 16:9; запись вписывает кадр в фиксированный размер с сохранением пропорций.
- **Частота кадров выбирается на странице: 10 / 15 / 20 / 24** (с 0.4.8, по умолчанию 15; раньше было жёстко 10). Сервер шлёт `"fps"` в `want`, хранит выбор в `orikly-server.json` (`"fps"`). Очки старее 0.4.8 поле игнорируют и шлют 10. Задержка — минимальная, без накопления. Всегда отправлять самый свежий кадр.
- Обычный кадр 480p (кадр Quest квадратный), JPEG 60. Развёрнутые очки — 960p, JPEG 80.
- Если канала не хватает — снижать качество (сначала JPEG, потом разрешение), а не частоту.
- **Eco (1 кадр/с остальным при развороте) — Paul отказался:** везде обычный поток. Не предлагать снова.
- Звук не нужен. На очках ничего не записывать; запись только на ноутбуке.

## Главное требование: одно подтверждение на очках

Захват экрана подтверждается на очках **один раз** (системное окно MediaProjection → «Pantalla completa» → «Empezar»), дальше держится постоянно. Трансляцию и запись запускают и останавливают с ноутбука («Стоп» = закрыть поток, захват на очках не останавливается).
Новое подтверждение неизбежно после: перезагрузки очков, обновления APK, штатного каста Meta, закрытия приложения из списка запущенных; возможно — после сна (не проверено).
Без ADB окно согласия обойти нельзя (нет системной подписи) — не пытаться. **С 0.5.1:** после ADB-команды `appops set … PROJECT_MEDIA allow` система должна отдавать разрешение без окна (так в AOSP; на Horizon OS не проверено) — на этом построен автоперезапуск. Запасной путь, если понадобится: `AccessibilityService.takeScreenshot` (~3 кадра/с, на Quest под HMS может быть недоступен).

## H.264 (0.5.0) — главное изменение, читать первым

- **Очки:** `CaptureService` — `VirtualDisplay` (AUTO_MIRROR) рисует прямо во входную поверхность `MediaCodec` (H.264, аппаратный). Без ImageReader/JPEG. Пока никто не смотрит — кодировщика нет (`virtualDisplay.surface = null`). Сетка 640×360 0,5 Мбит/с, разворот 1280×720 2,5 Мбит/с (решения Paul), CBR, Baseline 3.1, ключевой кадр раз в 2 с, `KEY_MAX_FPS_TO_ENCODER` = выбранный FPS, `KEY_REPEAT_PREVIOUS_FRAME_AFTER` 200 мс (статичный экран), без B-кадров, `KEY_PRIORITY 0`, `KEY_LATENCY 1`; если кодировщик не принял — запасной формат без этих ключей. Смена hq/FPS → пересборка кодировщика (`virtualDisplay.resize` + новая поверхность). SPS/PPS (`BUFFER_FLAG_CODEC_CONFIG`) кладутся перед каждым ключевым кадром.
- **Протокол:** hello `codec:"h264"`; binary = 1 байт типа (1 — ключевой с SPS/PPS, 2 — обычный) + Annex B. `want` += `"key":true` (новый зритель → ключевой кадр). `status` += `codec`, `bitrate`, `bitrateScale`, `encoder`; `sysFps` = кадры/с из кодировщика.
- **Отправка (`RelayClient`):** кадры строго по порядку; окно подтверждений (3 всегда, до 16 без очереди); кадр старше 700 мс или очередь WebSocket > 256 КБ → выбросить накопленное, запросить ключевой, слать с него (иначе «мозаика»). Битрейт: перегрузка (выбросы или отклик > 2×min+150) → ×0,75 (не ниже 30%), 6 с спокойно → ×1,15. Частота не меняется.
- **Сервер (`h264.go`):** хранит кадры с последнего ключевого (до 600 / 8 МБ) — новый зритель сразу получает картинку; каждому зрителю — очередь (120 + GOP), переполнение → пропуск до следующего ключевого + запрос ключевого (не чаще 1/с). JPEG-очки работают параллельно (старый `watch`). `/stream/` (MJPEG) для H.264 → 415. `/api/devices` += `codec`.
- **Страница:** WebCodecs `VideoDecoder` (`optimizeForLatency`), строка кодека из SPS (`avcCodec`); декодируются все кадры, рисуется каждый декодированный; очередь декодера > 30 → сброс до следующего ключевого. JPEG определяется по `FF D8`. **WebCodecs работает только в безопасном контексте: `localhost` или HTTPS.** Для Azure + Tailscale — `tailscale serve` (https://<машина>.<tailnet>.ts.net), страница сама переходит на `wss://`; `sameOrigin` пускает `*.ts.net`.
- Убрано (решения Paul): обрезка View (кодировщик не режет; GPU-шаг не делали), локальный режим (страница как файл, `HttpServer.kt` на очках), автозапуск 0.4.13 (откат: по словам Paul, «сделано плохо, появилась задержка стрима» — к нему не возвращаться; автоперезапуск сделан заново в 0.5.1). Основа — 0.4.12.
- Проверено: компиляция Kotlin против публичного `android.jar`; сервер+страница с `orikly-testsender` (H.264-клипы ffmpeg, встроены через go:embed): декодирование 640×360/1280×720 24 к/с, переключение разворота, второй зритель посреди потока — картинка через ~60 мс, запись MP4. **На очках не проверено ничего из H.264** (кодировщик Quest, задержка, адаптация битрейта). Поведение при узком канале на модели не проверялось (тестовый отправитель не адаптирует битрейт).

### 1. Приложение на очках — `app/` (Kotlin, 2D-панель)

- `applicationId org.orikly.queststream`, `minSdk 29`, `targetSdk 34`, `compileSdk 35`. AGP 8.10.1, Kotlin 2.1.21, Gradle 8.14.3. Единственная зависимость — OkHttp 4.12.0 (WebSocket). Разметка экрана в коде, без ресурсов.
- Экран приложения на испанском: имя, строка с версией (с 0.5.7 сразу под именем — внизу её обрезало), IP/порт, «Servidor: …», «Estado: …», кнопка «Iniciar transmisión», диагностика; экран прокручивается (`ScrollView`). Подсказку «Pantalla completa / Empezar» убрали в 0.5.7 (Paul: не нужна, с ADB окна выбора нет).
- Захват: foreground service типа `mediaProjection` (сначала `startForeground`, потом `getMediaProjection`, `registerCallback` до `createVirtualDisplay`). `VirtualDisplay` (AUTO_MIRROR) сразу в 960p → `ImageReader` RGBA_8888 → Bitmap → JPEG. `PARTIAL_WAKE_LOCK`, WifiLock (LOW_LATENCY + HIGH_PERF).
- Отбор кадров по расписанию ровно каждые 1000/targetFps мс (простое «≥ интервала» давало меньше кадров). Система Quest отдаёт ~30 кадров/с (по диагностике), поэтому 15 — ровный делитель, 20 — с небольшим дрожанием интервалов. Пока никто не смотрит — JPEG не сжимается, кадр в памяти раз в секунду.
- Новые кадры система даёт только когда экран **меняется**: неподвижный/выключенный экран → новых кадров нет (на ноутбуке ~1 кадр/с повтора).
- **Диагностика:** каждый вызов `onImage` считается (`StreamState.systemFrames`), раз в 2 с — `systemFps` (кадры/с от самой системы, до отбора 10 к/с). Также размер захвата, частота экрана (`Display.refreshRate`), `Build.DISPLAY`. Видно на экране очков («Diagnóstico: sistema … fps · enviados …») и на плитке ноутбука.
- Файлы: `CaptureService.kt` (захват, сжатие, лестницы качества), `StreamState.kt` (общее состояние, константы), `RelayClient.kt` (связь с ноутбуком через интернет), `HttpServer.kt` (локальный режим), `DeviceInfo.kt` (имя, id, IP, батарея, RSSI), `MainActivity.kt`.
- Константы (`StreamState.kt`): `TARGET_FPS 10`, `TARGET_HEIGHT 480`, `HQ_HEIGHT 960`, `NORMAL_LADDER = (480,60) (480,50) (480,40) (400,40) (360,35) (300,30)`, `HQ_LADDER = (960,80) (840,70) (720,65) (600,60) (480,55) (400,45)`.
- Сборочные параметры из секретов: `STREAM_KEY`, `RELAY_URL` → `BuildConfig`.

### 2. Связь очки → ноутбук через интернет (`RelayClient.kt` ↔ `server/main.go`)

- Очки сами держат WebSocket: `wss://stream.orikly.org/push?key=STREAM_KEY` (адрес зашит в APK из секрета `RELAY_URL`). Ping 20 с (Cloudflare рвёт молчащие ~100 с). Переподключение 2 → 30 с.
- Протокол:
  - очки → сервер: text `{"type":"hello","id","name","model","version"}`; `{"type":"status",capturing,fps,sentFps,level,rtt,output,source,sysFps,capture,hz,os,battery,rssi,ip}` раз в 2 с при показе (иначе 10 с); binary = JPEG-кадр.
  - сервер → очки: `{"type":"want","on","hq","acks":true}`; `{"type":"ack"}` на каждый кадр.
  - Сервер передаёт `status` на страницу как есть (новые поля не требуют правки сервера).
- **Подтверждения (с 0.3.3):** при занятом окне отправляется самый свежий кадр, как только придёт ack. **Окно (с 0.4.8):** до 3 кадров в пути — всегда; до 8 — только если самый старый неподтверждённый кадр в пути < минимальный отклик за 30 с + 60 мс (очереди нет). Причина: при окне 3 частота ≤ 3/отклик (300 мс → 10 к/с, 1 с → 3 к/с) — у Paul фризы шли именно от этого. Модель (прокси с задержкой и лимитом): отклик 250 мс, 5 Мбит/с, 20 к/с — было 9,7, стало 19,3 к/с при той же задержке; при нехватке канала (1,5 Мбит/с) 10,6 к/с вместо 8,3, отклик ~480 вместо ~330 мс (лестница качества в модели не учитывалась). Без этого задержка росла с 0 до 5–7 с (кадры копились в Cloudflare/буферах при узком интернете ноутбука). Сторож: если 5 с нет ack — окно сбрасывается.
- Адаптация: за 2 с выброшено >10% кадров → ступень качества ниже; 6 с без потерь → выше. При развороте начинается с лучшей ступени HQ.
- Очки различаются по **`id` = ANDROID_ID**, не по имени: на Quest имя у всех одинаковое («Quest 3»), в 0.3.0 из-за этого очки вытесняли друг друга.
- Совместимость: старое приложение + новый сервер и наоборот работают (неизвестные поля игнорируются; acks включаются, только если обе стороны новые).

### 3. Программа-сервер на ноутбуке — `server/` (Go 1.24, gorilla/websocket)

- Один файл без установки: `orikly-server.exe` (Windows) и `orikly-server-mac` (универсальный arm64+x86_64; склеивается `server/fatmacho.py`, т.к. на Linux-раннере нет lipo; Go сам ставит ad-hoc подпись для arm64). В релиз Mac-версия идёт как `orikly-server-mac.zip` (zip сохраняет право на запуск).
- Слушает **только `127.0.0.1:8090`**. Ключ — в `orikly-server.json` рядом с программой (`{"key": "...", "port": 8090}`), спрашивается при первом запуске.
- Эндпоинты: `/push` (WebSocket очков, единственный доступный через туннель); локально: `/` (страница, встроена в программу через `go:embed index.html` — при сборке копируется из `viewer/index.html`), `/api/devices`, `/view/<id>[?hq=1]` (WebSocket кадров для плитки), `/stream/<id>` (MJPEG, для отладки). Запросы через Cloudflare несут `Cf-Connecting-Ip` → всё, кроме `/push`, отвечает 404.
- При запуске открывает браузер (Mac: `open -a "Google Chrome"`; Windows: браузер по умолчанию). Держит компьютер бодрствующим: Mac — `caffeinate -di -w <pid>`, Windows — `SetThreadExecutionState(ES_CONTINUOUS|SYSTEM|DISPLAY)` в отдельном закреплённом потоке (`console_windows.go`). Закрытая крышка всё равно усыпляет.
- Windows: QuickEdit консоли отключается (`console_windows.go`, без внешних зависимостей, `syscall` + `SetConsoleMode`; на других ОС — `console_other.go`) — клик в окно ставил программу на паузу до Enter и **останавливал поток** (так и было у Paul); лог пишется асинхронно (`console.go`, после ввода ключа), при зависшей консоли строки выбрасываются.
- Строки в окне: `connected: <имя> [<хвост id>] (...) from <ip>`, `disconnected: …`, `rejected a headset with a wrong key …: headset key N chars, laptop's key M chars, first difference at character K (вид символа); client "<User-Agent>"` (сам ключ не печатается). При запуске: `Key from <путь>: N characters.`
- **Журнал фризов и трафика** (`netstats.go`): пауза в кадрах >1 с у просматриваемых очков → `FREEZE start: …` (с последним rtt/quality/system от очков; system <2 → «static screen?») и `FREEZE end: … N s`; раз в 10 с при просмотре — `traffic: total N Mbit/s` и по каждым очкам Mbit/s, fps, KB/кадр, rtt, quality, system, самая длинная пауза, число фризов. Всё дублируется в `orikly-log-<дата>.txt` рядом с программой.

### 4. Страница наблюдателя — `viewer/index.html` (один файл, без зависимостей)

- Два режима: открыта программой-сервером по `http://` → **режим сервера** (очки находятся сами); открыта как файл `file://` → старый локальный режим по IP (Settings: ключ + IP).
- Плитки по `id`, подпись «Quest 3 · хвост id» при совпадении имён. **Классы (с сервера 0.4.10+):** вверху выбор класса (по умолчанию Class 1/2/3, ✎ — переименовать); у одних и тех же очков в каждом классе своё имя (ученик), клик по имени плитки — задать имя в текущем классе. Всё хранится в `orikly-server.json` (`class`, `classes: [{name, names: {id: имя}}]`), `/api/classes` (`classes.go`); Windows и Mac — разные файлы, переносить копированием. Старые имена из localStorage не переносились (решение Paul: с чистого листа). Журнал сервера пишет имя ученика: `Ana (Quest 3 [e0fe])`. Файл записи: `<класс>_<имя>_<дата>.mp4`. **Class list** (кнопка): журнал текущего класса — поле «имена через запятую» (обрезка пробелов, без пустых и повторов) + список всех известных очков с выпадающим списком имён; выбранное имя пропадает из списков остальных очков; «Save» → `POST /api/classes?assign=N` `{students, names}` (заменяет имена класса целиком), в классе хранится `students`. Приложение урока — общее для всех классов. Известные очки запоминаются (localStorage).
- Start / Stop на плитке, Start all / Stop all, галочка Record, «Choose folder…» (File System Access API; папка запоминается в IndexedDB).
- Кадры в режиме сервера — по **WebSocket на каждую плитку** (Chrome держит максимум 6 HTTP-потоков к одному адресу; MJPEG по HTTP при 7+ очках вставал в очередь). Рисуется только самый свежий кадр.
- **HQ-окна (с ноября 2026, решение Paul; раньше — один разворот на весь экран):** клик по плитке в сетке → плитка становится окном поверх страницы на весь экран, в высоком качестве (`hq=1`, пометка **HQ** внизу слева). Тянешь **правый верхний угол** (значок ⤢) — окно уменьшается/увеличивается как угодно; тянешь картинку — окно двигается. Окон сколько угодно, все в HQ, ограничения по трафику нет (Paul). Клик по картинке окна (без перетаскивания, < 5 px) → плитка возвращается на своё место в сетке, обычное качество. Esc — верхнее окно обратно. Размеры/положения после перезагрузки не сохраняются. Код — `hqWindowControls`/`openWindow`/`closeWindow` (pointer events, `.tile.win { position: fixed }`). Сервер не менялся: `hqViewers` у каждых очков свой. Проверено: Playwright + `orikly-testsender -count 3` (открыть, уменьшить за угол, сдвинуть, второе окно, оба 1280×720, клик → 640×360, Esc). Canvas `position:absolute` + `min-height:0` (раньше обрезались верх/низ).
- Запись: `canvas.captureStream` с **отдельного canvas фиксированного размера (480)** → MediaRecorder, кодек **`avc3`** (с `avc1` Chrome предупреждал о порче файла при смене размера), куски раз в 2 с в файл `Имя_дата_время.mp4`.
- На плитке: «Streaming · N fps» (реально дошедшие кадры), «⏱ N ms» (отклик очки→ноутбук), «⚠ quality −N» (очки снизили качество), батарея, RSSI; серая строка диагностики «модель · system N fps · sent N fps · capture WxH · screen WxH Hz» (подсказка при наведении: версия приложения и OS); «Capture stopped — tap Iniciar on headset»; «Offline — headset not connected».

## Cloudflare (домен `orikly.org`)

- Аккаунт Cloudflare ассоциации (`Office@orikly.org`). DNS домена `orikly.org` перенесён в Cloudflare (сайт и почта ассоциации — в тех же DNS-записях, **их не трогать**).
- Туннель (cloudflared), маршрут — **Published application**: `stream.orikly.org` → **`http://127.0.0.1:8090`** (тип **HTTP**).
- Почему public, а не private hostname: private требует WARP + вход в Zero Trust на каждых очках — на Quest под HMS нереально. Снаружи доступен только `/push` с ключом.
- **Отложенное решение Paul:** Cloudflare Access + Service Token. «Пропуск» (`CF-Access-Client-Id` / `CF-Access-Client-Secret`) зашивается в APK как ключ (секреты GitHub), очки шлют его в заголовках. Посторонние запросы отсекаются на стороне Cloudflare и **до ноутбука не доходят** — это главное. Делать, когда всё заработает.
- Проверка туннеля: при запущенной программе `https://stream.orikly.org/push` → **`forbidden`** = всё работает.

### Грабли Cloudflare, на которые уже наступили

| Симптом | Причина |
|---|---|
| 502 Bad Gateway | В маршруте HTTPS вместо HTTP или `localhost` вместо `127.0.0.1` (на Windows `localhost` → `::1`, а программа слушает `127.0.0.1`); или программа не запущена. |
| 1033 | Адрес ведёт на туннель без живых компьютеров: DNS-запись `stream` (CNAME `<Tunnel ID>.cfargotunnel.com`) указывает на **старый/удалённый туннель**. CNAME должен совпадать с **Tunnel ID** (Tunnel details), а не с Replica ID (Replica ID всегда другой). Новый туннель = новый Tunnel ID = старый CNAME перестаёт работать. |
| «This site can't be reached» | DNS-записи `stream` нет (удалили вместе с маршрутом) или облако серое (DNS only) — нужно Proxied. После исправления — сбросить DNS-кэш. |
| В логе cloudflared `Unauthorized: Tunnel not found` | На компьютере работает cloudflared с токеном удалённого туннеля. |
| `service is already installed` | Сначала `cloudflared service uninstall`. |
| Часть очков не появляется | Туннель работает на двух компьютерах сразу (две реплики) — Cloudflare делит очки между ними. Должна быть **одна** реплика. |
| `rejected a headset with a wrong key` | Ключ в `orikly-server.json` ≠ `STREAM_KEY` из GitHub (у Paul ключ вида `password_1234`). |

Внешний IP школы (через него приходят все очки): `185.197.91.241` — у всех очков одинаковый, различать по id.

## Два компьютера, один туннель

- В Cloudflare **один туннель `stream`**, маршрут `stream.orikly.org → http://127.0.0.1:8090`. Второй туннель не нужен: адрес в APK один, а hostname привязывается только к одному туннелю.
- **Windows (основной):** cloudflared стоит службой, запускается сам. Остановить/запустить: PowerShell от администратора `Stop-Service cloudflared` / `Start-Service cloudflared`.
- **Mac (разработка):** cloudflared **не службой**, а вручную в окне Терминала: `cloudflared tunnel run --token <токен>` (токен — из «Add a replica → macOS», только часть `eyJ…`). Закрыл окно — Mac ушёл из туннеля. Так Mac не перехватит очки во время урока.
- Правило: в Replicas всегда **один** компьютер. Иначе Cloudflare делит очки между компьютерами.
- Прошлая попытка: на Mac мог остаться сервис от удалённого туннеля `stream_vr_macos` → `sudo cloudflared service uninstall`, `sudo pkill cloudflared`; DNS-запись `stream-vr-mac` удалить.
- На Mac уже стоят Homebrew и cloudflared. `orikly-server.json` с Windows не переносится — ключ вводится заново (= `STREAM_KEY`). Google Drive for desktop на Mac ещё не стоит.
- Полные гайды для Paul: `ИНСТРУКЦИЯ-MAC.md`, `ИНСТРУКЦИЯ-WINDOWS.md` (переключение Mac ↔ Windows, обновление `.exe`, Google Диск, крышка).

## Автоперезапуск при включении, обновлении и после сна (0.5.1)

- **Задача Paul:** «автоматически, ещё раз автоматически» — ни одного касания на очках. Только при включении очков и при выходе из сна (посреди урока стрим почти не замирает: дети всё время в очках). Захват при сне слетает (Quest 3 — проверено Paul; 3S — не проверено).

  `adb shell appops set org.orikly.queststream PROJECT_MEDIA allow` — захват без окна «Empezar»;

  `adb shell dumpsys deviceidle whitelist +org.orikly.queststream` — система не усыпляет приложение (и разрешает фоновый запуск служб).
  `adb shell appops set org.orikly.queststream GET_USAGE_STATS allow` — не для перезапуска, а для «в каком приложении ученик» (`AppWatcher`, контроль приложения урока); выдан на шлемах с 0.5.6.
  Сохраняются после перезагрузки и обновления APK; после удаления приложения — повторить. Без первых двух автоперезапуск не включается (на экране очков видно, чего не хватает).

## Голос учителя → шлемы (0.5.9)

- **Задача Paul:** учитель говорит в микрофон ноутбука — слышат только выбранные шлемы. На плитке рядом со Start — **«Connect Voice»** (нажата: «Voice ●», зелёная); вверху **«Voice all»** / **«Voice off»**. Выбор любой: один, несколько, все. Голос независим от видео (Start не нужен). Только учитель → ученики (обратно не нужно), кнопки Mute не нужно, громкость — как выставлена в шлеме. Игру приглушать, голос — отчётливее.
- **Страница:** пока выбран хоть один шлем — микрофон включён (`getUserMedia`, echoCancellation/noiseSuppression/autoGainControl), AudioWorklet `pcm16k` (усреднение входных отсчётов → 16 кГц) → PCM 16 бит моно, куски 640 отсчётов = 40 мс → WebSocket `/voice`. Текст `{"targets":[id…]}` при каждом изменении выбора. `bufferedAmount` > 64 КБ — кусок не шлём (задержка не копится). Микрофон только на `localhost` или https (Tailscale). Ошибки — в `#voiceState` (не в `warn`: его стирает опрос сервера).
- **Сервер (`voice.go`):** `/voice` (localOnly + sameOrigin) → каждому выбранному шлему binary `[3] + PCM` через свою очередь (25 кусков ≈ 1 с, переполнение — выбросить старое), запись под `writeMu`. Журнал: `voice: on → N headset(s): …` / `voice: off`. Старые шлемы бинарное от сервера игнорируют.
- **Шлем (`VoicePlayer.kt`, `RelayClient.onMessage(bytes)`):** AudioTrack 16 кГц, `USAGE_ASSISTANCE_NAVIGATION_GUIDANCE` + `CONTENT_TYPE_SPEECH` (громкость потока «музыка»), запас 120 мс перед стартом, очередь не больше 0,4 с, `AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK` (приглушает приложения, которые соблюдают аудиофокус — часть VR-игр не соблюдает, тогда голос поверх), `LoudnessEnhancer` +8 дБ. Тишина 0,8 с → стоп и снятие фокуса. На экране шлема: «Voz del profesor: sonando ahora / hace N s / —». Голос приходит по соединению стрима → работает, пока работает `CaptureService` (с автоперезапуском — почти всегда).
- Трафик: 32 КБ/с ≈ 0,25 Мбит/с на шлем, пока голос включён. Задержка ≈ 0,3–0,5 с.
- Проверено: Playwright с поддельным микрофоном Chromium + `orikly-testsender -count 3` (тест-отправитель считает принятый голос): голос только выбранным (#1+#3 → только они, «Voice all» → все, снять #2 → без него, «Voice off» → ничего, микрофон выключен), ~31 КБ/с на шлем, в кусках настоящий сигнал. Компиляция Kotlin. **На шлеме не проверено:** звук, приглушение игр, задержка.

## Приложение урока и серийник (с 0.4.9)

- **Очки:** `AppWatcher.kt` раз в секунду читает `UsageStatsManager.queryEvents` (разрешение `PACKAGE_USAGE_STATS`, включается вручную в настройках «Доступ к истории использования»; после «Iniciar», если разрешения нет, приложение само открывает этот экран; автоматически выдать его нельзя). Текущее приложение — последнее обычное (есть значок запуска, не оболочка Quest: `com.oculus.vrshell`, `systemux`, Home и т.д.), состояние `running` / `paused` (меню Meta) / `closed` (все activity приложения DESTROYED). В status: `usageAccess`, `app` (название), `appPkg`, `appState`. `QUERY_ALL_PACKAGES` — чтобы видеть названия.
- **Серийник:** `DeviceInfo.serials` — все непустые ответы: `getSerial`, `Build.SERIAL`, `ro.serialno` / `ro.boot.serialno` (через `SystemProperties` и `getprop`); в status `serials`. Страница: если есть значение вида `[A-Za-z0-9]{8,}`, не `unknown` → в названии плитки «… · SN …»; иначе все ответы в серой строке. Работает ли на Quest — не проверено.
- **Сервер:** учитель вписывает приложение урока на странице (поле «Lesson app», подсказки — названия с очков), одно на класс, хранится в `orikly-server.json` (`lesson`), `/api/lesson`. `lesson.go`: `left`, если приложение ≠ урока (сравнение без регистра по названию или пакету), или урок `closed`, или ничего не открыто; меню (paused) — не выход. Страница: красная рамка + «⚠ Left lesson app: …»; журнал: `LEFT LESSON: …` / `back in lesson: …`.
